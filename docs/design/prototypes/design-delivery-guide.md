# 前端设计交付指导

本文约束新版前端的设计方法与验证口径，不替代业务任务说明，也不改变仓库的 `Git` 或部署策略。历史返工的主要原因是把一个连续交互拆成多次局部修补：先实现，再等用户发现不一致；验证只证明某个端点正确，随后把这一类问题视为已解决。改进方向是提前选对组件与交互模型，用完整操作链验收，并让交付结论严格对应证据。

## 一、哪些返工可以避免

| 编号 | 表现与证据 | 根因 | 后续做法 |
| --- | --- | --- | --- |
| A-01 | 模块切换在双按钮、轨道、菜单之间反复变化；同一轮桌面和手机使用不同选择方式 | 先改一个形态，没有先定义同一功能在不同视口下的行为 | 先列展开、收起、手机的选择方式与状态；方向和尺寸可以不同，选择、当前项和关闭语义应一致 |
| A-02 | 底栏经过多轮自定义修补，最后才采用 `TabMenu`；主题行混用按钮样式与导航行 | 只复用了基础按钮，没有提前评估能承担整段交互的现成组件 | 在当前安装版本中查候选组件和公开接口，先验证原生用法，再补应用布局 |
| A-03 | 图文变色不同步，出现闪烁与分步生效 | 把按下、松开、路由提交和动画结束分别实现、分别检查 | 一次走完操作链，同时检查颜色、底色、字重、焦点与业务选中状态 |
| A-04 | 已验证收放前后坐标一致，用户仍看到过程中抖动、文字漏出 | 用两个静态端点代替动画过程 | 检查中间帧和快速反向；关联属性共用进度，边界裁切与最小宽度明确 |
| A-05 | 菜单能点开被当作通过，但收起按钮实际过窄，点击周边无响应 | 仅验证一次触发成功，未覆盖完整可见区域；错误宽度覆盖破坏了纯图标按钮尺寸 | 同时检查根节点尺寸、可见形状内的边缘命中、相邻对齐和键盘焦点；先删除错误覆盖 |
| A-06 | 面板无横向溢出，却仍有多余标题、分隔线贴控件、空白和过高工具区 | 把“放得下”当成“空间用得好”；容器默认值代替了布局判断 | 先决定铺满、限宽或按内容；按有效操作与占屏面积评估结构，优先减冗余分区，保持触控尺寸 |
| A-07 | 只改了一个强调色，边框和侧栏仍残留旧色；底栏和更多的悬停行为又不一致 | 只检查主色和单个组件，没有检查共享样式的作用范围 | 同一组中检查背景、边框、选中、按下、悬停与焦点；明确手机布局和鼠标桌面的反馈规则 |
| A-08 | 审核文件不断追加“本节覆盖上方”，顶部还保留旧模块记忆、显式系统选项等规则 | 历史日志代替了当前契约；下轮必须重新推算最终决定 | 顶部维护一份当前契约，历史按时间保留；新决定同时更新当前摘要与实际消费它的文档 |

可点击范围、状态连续、组件一致性和空间利用本来就是交互设计的一部分，不能归因于用户“太关注细节”。

## 二、不要把正常决定演进写成历史错误

| 编号 | 决定演进 | 正确理解 |
| --- | --- | --- |
| B-01 | 从文字切换到图标、选择轨道、调整更多的形态 | 存在正常视觉探索；但一旦方向明确，后续应保持，不应在修小问题时擅自换另一套交互 |
| B-02 | 移除退出登录 | 初版有来源，并非凭空添加；用户后来取消，应更新范围与相关计划 |
| B-03 | 主题从三项改为两项隐式跟随 | 是明确的新行为要求。旧规则下手动固定不是错误；更新后才以新规则验收，并同步所有共享偏好入口 |
| B-04 | 任务置首、点击模块进入任务 | 入口顺序、首次默认、模块切换和上次位置恢复是不同决定，应分别解释和修改对应规则 |
| B-05 | 手机全局控件移到底部、面板全宽、模块切换后面板保持打开 | 包含用户对工作方式的进一步确认，原方案的空间判断不足可以复盘，但不能声称所有新取舍从一开始就是明示要求 |

缺陷需要修复和补验证；决定变化需要更新契约及受影响入口。已明确授权的修改直接落实，不为每个样式值重新询问许可。

## 三、制作前先做四件事

1. **用现有任务记录承载当前契约。** 把本轮会影响实现的决定写成少量可检查的句子；新决定覆盖旧决定时，先更新当前表，再追加历史说明。
2. **先验证库能力，再决定自定义范围。** 按“现成语义组件 → 公开属性／主题配置／插槽 → 必要组合”的顺序选择实现，检查项目实际安装的版本。应用仍负责业务地址、面板关闭条件、模块身份、响应式排列与主题语义；不能把用了几个 `Button` 当成复用了完整导航行为，也不能为维持自定义外观而隐藏原生标签、用透明层补点击、重画焦点框或修改依赖源码。
3. **一次决定跨视口结构。** 普通输入／组合通常限宽；已决定为全宽的手机底部面板随视口铺满；内容高度由有效操作决定。减少占用时先去掉重复标题、无意义标签、独立空行和过厚分区，再调整排列；不要以缩小真实点击面积换取紧凑。
4. **写出一次完整操作的状态序列。** 实现前回答“按下后什么变、松开后谁接管、业务状态何时提交、取消时如何恢复”，并核对默认／当前项、按住、松开并提交、过渡结束、取消或快速反向、键盘与刷新前后导航的可见状态。反馈相同不等于所有属性都要动画；异步业务不能照搬导航的即时选中逻辑，应有真实的等待、成功和失败状态。

## 四、验证要覆盖问题，而不是堆检查数量

| 已有检查 | 能证明 | 不能据此宣称 |
| --- | --- | --- |
| 构建、文档检查、设计文档治理测试 | 构建和对应文档合同通过 | 视觉、手感、响应式或动画已经完整通过 |
| 无横向溢出 | 当前宽度没有页面横向溢出 | 面板不浪费空间、标签不拥挤、触控舒适 |
| 展开与收起的端点坐标一致 | 两个静态状态的指定坐标一致 | 中间过程不抖动、不漏字、快速反向正常 |
| 图标中心点击成功 | 该位置可以触发动作 | 整个可见按钮都能点击 |
| 单次主题切换成功 | 该次选择生效 | 系统跟随、持久化及所有边框／浮层都正确 |

按改动选择最小的有效检查集：纯文案或静态局部样式只查改动位置与相邻小屏；结构、尺寸或固定区域查桌面、手机和一个中间宽度；主题或交互状态查生产／训练与浅／深的关键组合；组件替换或路由行为同时验鼠标与键盘、真实地址、返回与刷新、浮层焦点返回。缩窄浏览器不等于真机触摸验证；无法可靠观察的部分明确写为未完成。

同类问题再次出现时，先回看组件职责、状态交接和布局约束，避免继续追加第三种临时样式。有界检查不是带着已知错误宣称完成的理由。

## 五、每轮如何交付

每轮交付前用四行核对，完整范围和证据放回已有任务记录：

1. **本轮改变**：解决哪个用户可见问题，是否改变了原交互语义。
2. **实际验证**：场景、视口／输入、观察属性及结果。
3. **限制与状态**：哪些仍未观察，设计是否仍待用户审核。
4. **交付事实**：本地完成、提交、推送和部署分别说明；它们不是设计批准。
