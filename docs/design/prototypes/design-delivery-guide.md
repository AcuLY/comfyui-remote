# 前端设计交付指导

本文来自2026-09-11对 `R02-01` 首稿至 `27b9ed7f` 的对话、审核记录及提交复盘，适用于后续新版前端原型设计与局部调整。它约束设计方法与验证口径，不替代业务任务说明，不扩大当前制作范围，也不改变仓库的 Git 或部署策略。

这次返工的主要原因，是助手把一个连续的交互体验拆成了多次局部样式修补：先实现，再等用户发现不一致；验证只证明某个尺寸、端点或颜色正确，随后就把这一类问题视为已经解决。用户因此承担了本应由助手完成的跨状态、跨视口检查。改进方向是提前选对组件与交互模型，用完整操作链验收，并让交付结论严格对应证据。

本次是交付过程复盘，不是对当前页面重新运行一次视觉审计；文中测量值均注明为既有版本证据，不新增界面验收结论。逐轮原始记录见 [R02-01](reviews/R02-01.md)。

通用执行原则已集成到 [技能交付质量指引](../../../.agents/skills/impeccable/reference/delivery-quality.md)，由技能入口及组件设计、适配、动效、审计和收尾流程加载。技能指引负责可迁移的方法；本文继续保留项目案例、决定演进及具体基线。

## 一、哪些返工可以避免

| 编号 | 对话中的表现与证据 | 根因 | 后续做法 |
| --- | --- | --- | --- |
| A-01 | 模块切换在双按钮、轨道、菜单之间反复变化；同一轮桌面和手机使用不同选择方式 | 先改一个形态，没有先定义同一功能在不同视口下的行为 | 先列展开、收起、手机的选择方式与状态；方向和尺寸可以不同，选择、当前项和关闭语义应一致 |
| A-02 | 底栏经过多轮自定义修补，直到 `27b9ed7f` 才采用 `TabMenu`；主题行混用按钮样式与导航行，出现字号、间距、渐隐差异 | 只复用了基础按钮，没有提前评估能承担整段交互的现成组件 | 在当前安装版本中查候选组件和公开接口，先验证原生用法，再补应用布局 |
| A-03 | 图文变色不同步 → 绿、灰、绿闪烁 → 先变绿再加粗，分别在 `af3fe4f6`、`232ad72b`、`27b9ed7f` 处理 | 把按下、松开、路由提交和动画结束分别实现、分别检查 | 一次走完操作链，同时检查颜色、底色、字重、焦点与业务选中状态 |
| A-04 | 已验证收放前后坐标一致，用户仍看到过程中抖动、文字漏出；`4ae88c1f` 才统一进度与裁切 | 用两个静态端点代替动画过程；居中方式、标签插拔、宽度和透明度各有节奏 | 检查中间帧和快速反向；关联属性共用进度，边界裁切与最小宽度明确 |
| A-05 | 菜单能点开被当作通过，但收起按钮实际只有约15.2px宽，用户点击周边无响应 | 仅验证一次触发成功，未覆盖完整可见区域；`width: auto` 破坏了纯图标按钮尺寸 | 同时检查根节点尺寸、可见形状内的边缘命中、相邻对齐和键盘焦点；先删除错误覆盖 |
| A-06 | 面板无横向溢出，却仍有大标题、分隔线贴控件、独立主题行空白和过高工具区 | 把“放得下”当成“空间用得好”；容器默认值代替了布局判断 | 先决定铺满、限宽或按内容；按有效操作与占屏面积评估结构，优先减冗余分区，保持触控尺寸 |
| A-07 | 训练强调色已经变粉，边框和侧栏仍偏蓝绿；底栏和更多的悬停行为又不一致 | 只检查主色和单个组件，没有检查共享样式的作用范围 | 同一组中检查背景、边框、选中、按下、悬停与焦点；明确手机布局和鼠标桌面的反馈规则 |
| A-08 | 审核文件不断追加“本节覆盖上方”，顶部还保留旧模块记忆、显式系统选项等规则 | 历史日志代替了当前契约；下轮必须重新推算最终决定 | 顶部维护一份当前契约，历史按时间保留；新决定同时更新当前摘要与实际消费它的文档 |

这些缺陷不能归因于用户“太关注细节”。可点击范围、状态连续、组件一致性和空间利用本来就是交互设计的一部分。

## 二、不要把正常决定演进写成历史错误

| 编号 | 决定演进 | 正确理解 |
| --- | --- | --- |
| B-01 | 从文字切换到图标、选择轨道、调整更多的形态 | 存在正常视觉探索；但一旦方向明确，后续应保持，不应在修小问题时擅自换另一套交互 |
| B-02 | 移除退出登录 | 初版在 `IA-05/06` 中有来源，并非凭空添加；用户后来取消，应更新范围与相关计划 |
| B-03 | 主题从系统／浅／深三项改为两项隐式跟随 | 是明确的新行为要求。旧规则下手动固定不是错误；更新后才以新规则验收，并同步所有共享偏好入口 |
| B-04 | 任务置首、点击模块进入任务 | 入口顺序、首次默认、模块切换和上次位置恢复是不同决定。首次默认原本已是任务，旧位置恢复使切换时又进入项目；应解释并修改对应规则，不只换列表顺序 |
| B-05 | 手机全局控件移到底部、面板全宽、模块切换后面板保持打开 | 包含用户对工作方式的进一步确认。原方案的空间与一致性判断不足可以复盘，但不能声称所有新取舍从一开始就是明示要求 |

区分这两类不是降低质量要求，而是找到正确措施：缺陷需要修复和补验证；决定变化需要更新契约及受影响入口。已明确授权的修改直接落实，不为每个样式值重新询问许可。

## 三、制作前先做四件事

### 1. 用现有任务记录承载当前契约

引用已登记的任务编号、用户目的、包含与排除范围。把本轮实际会影响实现的决定写成少量可检查的句子；不用再创建一份空模板，不临时拆出不存在的子任务。

对导航至少区分以下问题。下表是 `R02-01` 当前例子，不是其他页面的通用答案。

| 触发 | 当前预期 |
| --- | --- |
| 无有效记录的首次访问 | 进入生产任务 |
| 直接页面地址、刷新及浏览器前后 | 保留或恢复具体有效入口；无效地址按已定规则回退 |
| 点击生产／训练轨道 | 进入对应任务，不恢复旧模块项目入口 |
| 在更多中切换模块 | 面板保持打开，模块及任务入口同步更新 |
| 在更多中进入具体工具 | 导航并关闭面板 |
| 选择异于系统当前颜色的主题 | 固定此选择并持久保存 |
| 选择与系统当前颜色相同的主题 | 恢复实时跟随；没有独立系统选项 |
| 已固定后系统颜色变化 | 不因系统暂时与选择相同而自动解除固定 |

新决定覆盖旧决定时，先更新这类当前表，再追加历史说明。不要要求下一个执行者从十几段修订中推导当前规则。

### 2. 先验证库能力，再决定自定义范围

按“现成语义组件 → 公开属性／主题配置／插槽 → 必要组合”的顺序选择实现。检查项目实际安装的版本，不凭其他版本文档或印象写接口。

| 要回答的问题 | 应有的简短记录 |
| --- | --- |
| 组件是否匹配业务动作 | 例如 `TabMenu` 可承载一级导航；目录树不能因为可选择就成为所有业务的通用选择器 |
| 组件原生负责什么 | 选中、方向键、焦点、模态约束等具体职责 |
| 应用仍负责什么 | 业务地址、面板关闭条件、模块身份、响应式排列及主题语义 |
| 要定制什么，为什么 | 指明公开接口及必要布局；不能把用了几个 `Button` 当成复用了完整导航行为 |

原生 HTML 链接和操作按钮仍然合适，不需要机械地把所有元素换成库组件。也不能为了维持自定义外观而隐藏原生标签、用透明层补点击、重画焦点框或修改依赖源码。采用原生组件后仍须验证应用集成，例如键盘激活是否真的更新地址，而不只是改了选中项。

### 3. 一次决定跨视口结构

先明确每类容器的策略：普通输入／组合通常限宽；已决定为全宽的手机底部面板随视口铺满；内容高度由有效操作决定。不要把同一个最大宽度规则套到所有容器。

检查顶部页面操作区、底部固定区、安全区和内容留位的关系。减少占用时，先去掉重复标题、无意义标签、独立空行和过厚分区，再调整排列；不要以缩小真实点击面积换取紧凑。现有36px普通桌面控件、40px触控普通控件与44px图标动作各有适用范围，不能互相替代。

### 4. 写出一次完整操作的状态序列

对交互性控件，在实现前回答“按下后什么变、松开后谁接管、业务状态何时提交、取消时如何恢复”。

| 阶段 | 同时核对 |
| --- | --- |
| 默认／当前项 | 颜色、字重、图标、可访问名称和业务位置一致 |
| 按住 | 图标、文字、底色共享反馈，不提前伪造导航或保存成功 |
| 松开并提交 | 按下态结束与选中态生效连续交接，不回落一帧默认色 |
| 过渡结束 | 相关属性一起到达目标；不能出现变色后再跳字重 |
| 取消、重复点击或快速反向 | 不残留按下态、旧浮层、失焦或动画端点跳跃 |
| 键盘、刷新和前后导航 | 可见状态与实际行为一致，不只验证鼠标路径 |

反馈相同不等于所有属性都要动画。先保持结构和字重稳定，再对有价值的颜色或位置做短过渡；普通过渡足够时不引入额外状态机。确需多个属性严格同步时，可共享进度，但 `R02-01` 的160毫秒和计算公式不是全项目强制数值。异步业务不能直接照搬导航的即时选中逻辑，应有真实的等待、成功和失败状态。

## 四、验证要覆盖问题，而不是堆检查数量

### 证据能证明什么

| 已有检查 | 能证明 | 不能据此宣称 |
| --- | --- | --- |
| 构建、文档检查、19项设计文档治理测试 | 构建和对应文档合同通过 | 视觉、手感、响应式或动画已经完整通过 |
| 无横向溢出 | 当前宽度没有页面横向溢出 | 面板不浪费空间、标签不拥挤、触控舒适 |
| 展开与收起的端点坐标一致 | 两个静态状态的指定坐标一致 | 中间过程不抖动、不漏字、快速反向正常 |
| 图标中心点击成功 | 该位置可以触发动作 | 整个可见按钮都能点击 |
| 57帧没有灰色闪回 | 当时采样的颜色交接连续 | 字重不跳、底色有渐变、键盘导航完整 |
| 单次主题切换成功 | 该次选择生效 | 系统跟随、持久化及所有边框／浮层都正确 |

已知截图存在宿主缩放失真时，记录实际视口和限制。布局读数可以补尺寸证据，不能替代对空间、颜色层次和可读性的视觉判断。无法可靠观察的部分应明确写为未完成，不用测试数量掩盖它。

### 按改动选择最小的有效检查集

| 改动类型 | 本轮优先检查 |
| --- | --- |
| 纯文案或静态局部样式 | 改动位置、相邻元素和最容易受影响的小屏；不跑无关全应用流程 |
| 结构、尺寸或固定区域 | 桌面、手机、一个中间宽度；涉及断点时检查临界两侧，涉及底部面板时检查短横屏与安全区 |
| 主题或交互状态 | 在代表视口看生产／训练与浅／深的关键组合，检查边框、选中、按下、焦点及浮层，不机械穷举所有宽度 |
| 动画或连续反馈 | 完整按下到提交序列；相关属性的中间帧、快速反向和减少动态效果 |
| 组件替换或路由行为 | 鼠标与键盘、真实地址、返回与刷新、浮层打开关闭及焦点返回 |

`R02-01` 曾在320／393px手机、600～767px中间宽度、768～1199px窄栏和1200px以上展开区出现不同问题。后续按实际断点选样本，不把“测过393和1440”视为所有响应式问题都被覆盖。

本项目手机布局已明确不使用悬停底色，保留按下、选中和键盘焦点；鼠标桌面保留悬停。检查时区分布局宽度与输入能力，缩窄浏览器本身不等于真机触摸验证。

### 有界检查，但不留下已知缺陷

采用 [设计技能](../../../.agents/skills/impeccable/SKILL.md) 的有界检查原则：完整制作后，将适用的桌面、手机和状态检查放在同一轮；把发现的问题汇总修复，再做一次针对性确认。新失败或新的用户要求才触发必要复查，不反复扩大审美检查范围。

同类问题再次出现时，先回看组件职责、状态交接和布局约束，避免继续追加第三种临时样式。已复现的问题仍需解决；有界检查不是带着已知错误宣称完成的理由，也不是停止已授权工作的许可。

## 五、每轮如何交付

每轮交付前，用下面四行核对即可；完整范围和证据放回已有任务记录，不另造一套任务管理文件。

1. **本轮改变**：解决哪个用户可见问题，是否改变了原交互语义。
2. **实际验证**：场景、视口／输入、观察属性及结果；不要只写“测试通过”。
3. **限制与状态**：哪些仍未观察，设计是否仍待用户审核。
4. **交付事实**：本地完成、提交、推送和部署分别说明；它们不是设计批准。

例如，“按住与释放时图文同色，动画字重尚未检查”比“交互完全同步”准确；“构建及文档检查通过，623px按下到选中采样无颜色回落”比只列测试数量有用。

当前契约、真实产物和审核状态应在下一轮开始前一致。这个一致性维护由助手承担，不应再让用户通过重复指出同一类细节来完成。
